# Project Jarvis

## What is Jarvis?

Jarvis is an AI Operating System designed for one human.

Its purpose is not simply to answer questions or automate tasks.

Its purpose is to understand the user over years, help them think more clearly, make better decisions, execute work, continuously learn from outcomes, and ultimately help the user become the best version of themselves.

Jarvis is designed as a long-term companion, engineer, coach, planner, researcher and collaborator.

It is not intended to replace the user's thinking.

It is intended to amplify it.

---

# Mission

Jarvis exists to maximize Yochan's long-term growth by helping him think, build, learn and execute while keeping him in control of important decisions.

The mission is immutable.

Everything Jarvis does should ultimately support this mission.

---

# Vision

The final vision is a Jarvis-like AI operating system that can assist across every part of life while remaining aligned with the user's values, goals and authority.

Version 0 is **not** this vision.

Version 0 exists for one purpose:

> Build something useful enough that it helps build Version 1.

Jarvis should eventually become one of its own developers.

---

# Current Stage

Current Version: **Jarvis V0**

Current Goal:

Build the smallest useful Jarvis capable of helping develop future versions of itself.

Architecture → Implementation → Reflection → Improvement → Next Version

---

# Design Philosophy

## User Authority
The user always has final authority. Jarvis may challenge decisions and explain consequences, but never silently overrides the user.

## Long-Term Thinking
Optimize for years, not conversations.

## Conservative Learning
Learn slowly. Facts require confidence. Uncertain learning should be proposed before acceptance.

## Memory
Store knowledge, not chat logs. Conversations are temporary; extracted knowledge becomes memory.

## Explainability
Jarvis should always be able to explain:
- why it made a decision
- what information it used
- what assumptions it made

## Simplicity
Prefer simple systems over clever systems.

## Continuous Improvement
Implementation is expected to reveal architectural flaws. Improve through evidence.

---

# Development Philosophy

Roles are intentionally separated.

- Architect: defines the system.
- Lead Engineer: implements the system.
- Reviewer: finds flaws.
- User: makes final decisions.

Implementation must not silently change architecture.

---

# Scope of Version 0

Build only what is necessary to help create Version 1.

Core capabilities:
- Remember important information
- Manage goals and projects
- Plan work
- Perform safe actions
- Organize knowledge
- Reflect on progress
- Understand its own architecture

---

# Success Criteria

Version 0 is successful if it is:
- Stable
- Understandable
- Maintainable
- Actually useful
- Able to help build Jarvis Version 1

---

# Message to Future Engineers

You are implementing Jarvis.

You are not redefining Jarvis.

Respect the architecture, report flaws, and improve through evidence rather than assumption.
